# 30 — コーディング規約

このルールは Phase 4 (`/implement TASK-XXX`) でのみ適用される。設計フェーズの自然言語ドキュメントには適用しない。

## 言語別の前提

- 言語が決まっていない場合は **TypeScript (Node.js, ESM)** を仮定する。決まっている場合は `docs/10-basic-design/02-architecture.md` の「技術選定」セクションに従う。
- フレームワークは設計ドキュメントの決定に従う。Claude が独断で導入してはならない。

## 基本方針

1. **設計ドキュメントの ID を実装ファイルにコメントで残す**。
   ```ts
   // SCR-001 / API-010 — ログイン画面の送信ハンドラ
   ```
   そのうえで、TASK-ID は **コミットメッセージ** に書く。コードコメントには TASK-ID を書かない（消化後に陳腐化するため）。
2. 1 ファイルは 1 つの責務に絞る。300 行を超えたら分割を検討。
3. 例外は黙って握り潰さない。`try/catch` するなら必ずログまたは再 throw。
4. テストは振る舞いを書く。実装の詳細を写経するスナップショットだけのテストを書かない。

## 命名

- ファイル: `kebab-case.ts`、ただし React コンポーネントは `PascalCase.tsx`
- 関数・変数: `camelCase`
- 型・クラス: `PascalCase`
- 定数: `UPPER_SNAKE_CASE`（モジュール直下のみ）
- DB のカラム: 設計の `DB-XXX.md` の表記に従う

## コメント

- 既定: コメントを書かない。識別子で意図が読めるようにする。
- 書いてよい例: 仕様で必須の不変条件、外部 API の癖、アルゴリズムの非自明な選択理由。
- 書いてはいけない例: TASK-ID、変更履歴、レビューでのやりとり、未来の予定（`// TODO: あとで` は禁止。代わりに新しい `TASK-XXX` を起こす）。

## エラーハンドリング

- ユーザ入力境界・外部 API 境界では必ず検証する。内部関数の引数はシステムの不変条件を信頼する。
- 例外メッセージは **デバッグに必要な値を含める**。ユーザ向けメッセージは `i18n` 層で別途定義する。

## テスト

- 単体テストは設計の `TEST-XXX` と 1 対 1 で対応させる。
- テスト名は仕様文。例: `it("REQ-001 / TEST-010: ログイン失敗時にエラーを表示する")`
- 結合テスト・E2E は `tests/integration/`、`tests/e2e/` に分ける。

## ログ

- 構造化ログ（JSON）を基本とする。
- PII（個人情報）をログに乗せない。`docs/02-requirements/glossary.md` の PII リストを参照。

## バージョン管理

- ブランチ: `feature/TASK-XXX-short-slug`
- コミットメッセージ: `<type>(TASK-XXX): 概要` / 例: `feat(TASK-010): add login API client`
- 1 PR = 1 タスクが基本。例外時は PR 説明欄に理由を書く。

## やってはいけないこと

- 設計ドキュメントに無い機能を勝手に追加する
- 既存ファイルを TASK 範囲外で大規模に書き換える（リファクタリングは独立 TASK にする）
- `eslint-disable`, `@ts-ignore`, `any` を理由なく使う
- バックワードコンパチのためだけにコードを残す（要件ドキュメントに記載がない限り）
