# API-002 — submit（提出 server function）

## 概要

投稿者本人が自分の `draft` 提案を倫理ガード 3 種 + PolicyAgreement 同意 + 必須項目検証を経て `submitted` に遷移させ、初回 submit 時に PolicyAgreement レコードを生成する mutation 系 server function（UC-002 / UC-014 / UC-016）。

## エンドポイント

```
POST /v1/proposals/{id}/submit
```

> 注記: TanStack Start の server function として実装する（論理名 `submit`）。本詳細設計では将来の REST 公開も視野に入れ、URL 表現として `POST /v1/proposals/{id}/submit` を正規化する。実体は server function ID と HTTP パスの両方の意味で参照可能。

## 認可

- **レベル**: `authenticated`（投稿者本人 / `user` 以上）
- **必要ロール**: `user`（`reviewer` / `admin` も `user` を兼ねる場合のみ可だが、author 一致が必須）
- **リソース所有者一致**: `proposals.author_id == viewer.user_id` を `assertOwner(viewer, proposal_id)` で検証
- **CSRF 検証**: Origin / Sec-Fetch-Site=same-origin（NFR-006）。違反時は **403 CSRF_DENIED**（B-2 確定、暫定統一の認可違反 404 とは別概念）+ logger `403_reason=cross_site`
- **レート制限**: MVP 対象外（Q-013 暫定）
- **公開バイパス**: 対象外（必ず `authorize()` を通過、NFR-003 / `BR-AUTHZ-03`）

## リクエスト

### パスパラメータ

| 名前 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | string (uuid v7) | yes | 対象 proposal の ID（`status='draft'`、author 一致が前提） |

### クエリパラメータ

なし。

### ヘッダ

| 名前 | 必須 | 説明 |
| --- | --- | --- |
| `Cookie` | yes | モック認証 cookie（`HttpOnly` / `Secure` / `SameSite=Lax` 以上、NFR-006）。許可リスト外は `401` |
| `Origin` | yes | 同一オリジンであること（NFR-006 CSRF 検証） |
| `Sec-Fetch-Site` | yes | `same-origin` を期待 |

### ボディ

```json
{
  "visibility": "internal",
  "ethics_check_personal_info": true,
  "ethics_check_no_libel": true,
  "ethics_check_publicity_acknowledged": true,
  "policy_agreement_consent": true,
  "expected_version": 0
}
```

#### スキーマ（Zod 暫定、Phase 5 で確定）

| フィールド | 型 | 必須 | 制約 |
| --- | --- | --- | --- |
| `visibility` | string | yes | enum: `private` / `internal` / `public`（DB-003 CHECK と整合、REQ-013） |
| `ethics_check_personal_info` | boolean | yes | `true` のみ受理。`false` は 400 VALIDATION_ERROR（`BR-GUARD-01`） |
| `ethics_check_no_libel` | boolean | yes | 同上 |
| `ethics_check_publicity_acknowledged` | boolean | yes | 同上 |
| `policy_agreement_consent` | boolean | yes | `true` のみ受理。`false` は 400（`BR-GUARD-02`） |
| `expected_version` | integer | yes | 楽観ロック用、proposal の現在 `version`。値が DB と一致しない場合 409 CONFLICT（`BR-REVIEW-02`） |

> **`policy_version` はリクエストに含めない（M-4 確定）**: クライアントから受け取らず、server-side が同じソース（API-018 が参照する policy storage、MVP では in-memory 定数 `mvp-initial`）から最新版を取得して PolicyAgreement に保存する。クライアント信頼を排除して改竄リスクを除去（NFR-003）。画面側 (SCR-004) は表示用に API-018 で取得するが、API-002 への送信は不要。

> 注: `title` / `body` 本文は本 API では受け取らない。draft 段階で別途保存済みであることを前提とする（DB-003 の「draft 作成 / 編集」付帯処理参照）。

## レスポンス

### 200 OK

```json
{
  "proposal_id": "01HXYZ...",
  "status": "submitted",
  "submitted_at": 1746360000000,
  "version": 1,
  "policy_agreement_id": "01HXYZ-pa..."
}
```

#### スキーマ

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `proposal_id` | string (uuid v7) | yes | 対象 proposal の ID（パス引数と同一） |
| `status` | string | yes | 遷移後の status。常に `"submitted"` |
| `submitted_at` | integer | yes | 遷移時刻（Unix epoch millis） |
| `version` | integer | yes | 遷移後の version（+1 された値） |
| `policy_agreement_id` | string (uuid v7) | yes | 生成または既存の PolicyAgreement ID（初回 submit で新規生成、再 submit には到達しない設計） |

### 4xx / 5xx

| ステータス | アプリコード | 状況 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 必須項目欠落 / 倫理ガード 3 種いずれか false / `policy_agreement_consent=false` / `visibility` 不正値 |
| 401 | `UNAUTHENTICATED` | cookie なし、または許可リスト外（`403_reason=not_authenticated`） |
| 404 | `NOT_FOUND` | proposal が存在しない / author 不一致（`403_reason=not_owner_resource`、暫定統一） |
| 409 | `CONFLICT` | `expected_version` が DB と不一致（**楽観ロック失敗のみ**、M-8 確定） |
| 422 | `BUSINESS_RULE_VIOLATION` | proposal の status が `draft` 以外（draft → submitted 以外の遷移） / PolicyAgreement の `ux_policy_agreements_proposal` UNIQUE 違反（既存の同意レコードあり、本来到達しないがフェイルセーフ） / その他ビジネスルール違反（M-8 確定） |
| 500 | `INTERNAL_ERROR` | DB 書き込みエラー等の想定外例外 |

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "倫理ガードチェックボックスがすべて確認されている必要があります",
    "field_errors": [
      { "field": "ethics_check_no_libel", "code": "MUST_BE_TRUE" }
    ]
  }
}
```

## 副作用 / DB アクセス

| DB | 操作 | 備考 |
| --- | --- | --- |
| DB-003 (proposals) | write (UPDATE, CAS) | `WHERE id=? AND version=expected_version` で `status='draft' → 'submitted'`、`submitted_at=now`、`current_policy_agreement_id`、`updated_at=now`、`version=version+1` |
| DB-005 (policy_agreements) | write (INSERT) | 初回 submit のみ。`(id, user_id=viewer.user_id, proposal_id, policy_version, agreed_at=now)` を生成。**`policy_version` は server-side が API-018 と同じソース（MVP では in-memory 定数 `mvp-initial`）から取得**（M-4 確定、クライアント送信値は受理しない）。`ux_policy_agreements_proposal` UNIQUE 制約で重複生成を防止（既存があれば 422 BUSINESS_RULE_VIOLATION に正規化） |
| DB-004 (audit_logs) | append (INSERT) | 成功時のみ末尾で append（後述「AuditLog 書き込み」） |
| DB-006 (users) | read | `findById(viewer.user_id)` で actor の roles を確認（`BR-AUTHZ-03`） |

> **書き込み順序**: (1) authorize → (2) validate → (3) DB-003 CAS UPDATE → (4) DB-005 INSERT（初回のみ）→ (5) DB-004 append。いずれかが失敗したら以降の書き込みを実行しない（`BR-AUDIT-03`）。トランザクション境界は Phase 5 で D1 採用時に確定。

## AuditLog 書き込み

| フィールド | 値 |
| --- | --- |
| `action` | `submit` |
| `actor_id` | `viewer.user_id` |
| `actor_role` | `viewer.roles` のスナップショット（DB-004 と整合）。**単一ロール時はそのまま**（例: `user`）、**複数ロール OR 合成時はカンマ区切り**（例: `reviewer,admin`、m-02 整理）。記録時点の値で固定（後でユーザの roles を変更しても本ログは不変、DB-004 不変条件 4） |
| `target_proposal_id` | パス引数 `id` |
| `before_status` | `draft` |
| `after_status` | `submitted` |
| `before_visibility` / `after_visibility` | NULL（visibility 変更ではない） |
| `reason` | 任意（Q-019 暫定）。本 API ではリクエストに `reason` を持たないため常に NULL（API-007 / API-009 と整合: 空白のみは null として扱う、m-03 確定） |
| `policy_agreement_id` | 生成した PolicyAgreement の ID（初回）。NOT NULL（DB-004 不変条件 6 と整合） |
| `created_at` | `now()` |

`reason` 必須要否: **任意**（Q-019 暫定）。

## 認可拒否時の挙動

| 拒否シナリオ | HTTP | logger `403_reason` |
| --- | --- | --- |
| cookie なし | 401 | `not_authenticated` |
| cookie あるが許可リスト外 | 401 | `not_authenticated` |
| ログイン済だが `proposals.author_id != viewer.user_id`（他人の draft を提出） | 404 | `not_owner_resource` |
| Origin 不一致 / Sec-Fetch-Site != same-origin | **403** | `cross_site` |

副作用は **発生させない**（`BR-AUDIT-03`、NFR-003 AC）。

## バリデーション規約

- ライブラリ: **Zod**（暫定、Phase 5 で確定）
- 検証順序:
  1. ボディスキーマ（型 / 必須）→ 失敗で即 400
  2. 倫理ガード 3 種すべて `true` → 1 つでも `false` で 400（`BR-GUARD-01`）
  3. `policy_agreement_consent === true` → false なら 400（`BR-GUARD-02`）
  4. `visibility` enum 検証（DB-003 CHECK と二重防御）
  5. authorize（owner 一致 + role）
  6. proposal 取得 → `status === 'draft'` を確認、それ以外なら 422
  7. `expected_version` 一致を CAS UPDATE で検証、失敗で 409

## エラーコード

| HTTP | コード | 用途 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | スキーマ違反 / 倫理ガード未確認 / 同意なし |
| 401 | `UNAUTHENTICATED` | cookie 不正・未認証 |
| 404 | `NOT_FOUND` | proposal 存在しない / author 不一致（暫定統一） |
| 409 | `CONFLICT` | 楽観ロック失敗のみ（M-8 確定、PolicyAgreement UNIQUE 違反は 422 へ） |
| 422 | `BUSINESS_RULE_VIOLATION` | `status != 'draft'` / PolicyAgreement UNIQUE 違反 / その他ビジネスルール違反 |
| 500 | `INTERNAL_ERROR` | 想定外例外 |
