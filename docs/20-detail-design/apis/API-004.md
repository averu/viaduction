# API-004 — approve（承認 server function）

## 概要

担当中の `reviewer` または `admin` が `in_review` の提案を `approved` に遷移させる mutation。reason 必須（`BR-REVIEW-01`）。`assignee_id` は NULL に戻る。

## エンドポイント

```
POST /v1/proposals/{id}/approve
```

## 認可

- **レベル**: `authenticated`
- **必要ロール**: `reviewer` または `admin`
- **リソース所有者一致**: **不要 (B-3 撤回)**。reviewer / admin であれば assignee に関わらず判定可（業務継続性のため、要件 REQ-003 / BR-REVIEW-* に従う）。`assignee_id` は補助情報として DB-003 に保持、判定の権限制約には未使用
- **CSRF 検証**: Origin / Sec-Fetch-Site=same-origin（NFR-006）
- **レート制限**: MVP 対象外（Q-013 暫定）

## リクエスト

### パスパラメータ

| 名前 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `id` | string (uuid v7) | yes | `status='in_review'` 前提 |

### ボディ

```json
{
  "reason": "条例第3条に基づき市民意見として妥当と判断",
  "expected_version": 2
}
```

#### スキーマ

| フィールド | 型 | 必須 | 制約 |
| --- | --- | --- | --- |
| `reason` | string | **yes** | 1〜4000 文字、空白のみ不可（`BR-REVIEW-01`） |
| `expected_version` | integer | yes | CAS 用 |

### ヘッダ

| 名前 | 必須 | 説明 |
| --- | --- | --- |
| `Cookie` | yes | 認証 cookie |
| `Origin` | yes | 同一オリジン |
| `Sec-Fetch-Site` | yes | `same-origin` |

## レスポンス

### 200 OK

```json
{
  "proposal_id": "01HXYZ...",
  "status": "approved",
  "version": 3,
  "audit_log_id": "01HXYZ-al..."
}
```

#### スキーマ

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `proposal_id` | string | yes | 対象 ID |
| `status` | string | yes | `"approved"` |
| `version` | integer | yes | +1 |
| `audit_log_id` | string | yes | append された AuditLog ID |

### 4xx / 5xx

| ステータス | アプリコード | 状況 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | reason 空 / 文字数超過 |
| 401 | `UNAUTHENTICATED` | cookie なし |
| 404 | `NOT_FOUND` | role 不足 / 自身が assignee でない / proposal 不存在 |
| 409 | `CONFLICT` | 楽観ロック失敗 |
| 422 | `BUSINESS_RULE_VIOLATION` | `status != 'in_review'` |
| 500 | `INTERNAL_ERROR` | 想定外 |

## 副作用 / DB アクセス

| DB | 操作 | 備考 |
| --- | --- | --- |
| DB-003 (proposals) | write (UPDATE, CAS) | `WHERE id=? AND version=expected_version AND status='in_review'` で `status='approved'`、`assignee_id=NULL`、`approved_at=now()`（B-2 / MAJOR-3）、`updated_at=now`、`version+1`。**B-3 撤回**: assignee_id 一致条件は CAS から削除 |
| DB-004 (audit_logs) | append (INSERT) | reason 必須 |
| DB-006 (users) | read | role 確認 |

## AuditLog 書き込み

| フィールド | 値 |
| --- | --- |
| `action` | `approve` |
| `actor_id` | `viewer.user_id` |
| `actor_role` | スナップショット |
| `target_proposal_id` | パス引数 |
| `before_status` | `in_review` |
| `after_status` | `approved` |
| `reason` | NOT NULL |
| `policy_agreement_id` | NULL |
| `created_at` | `now()` |

`reason` 必須要否: **必須**。

## 認可拒否時の挙動

| 拒否シナリオ | HTTP | logger `403_reason` |
| --- | --- | --- |
| cookie なし | 401 | `not_authenticated` |
| role が `user` のみ / `auditor` / `guest` | 404 | `insufficient_role` |
| ~~`assignee_id != viewer.user_id`~~ **撤回 (B-3)**: assignee 一致は要求しない、reviewer/admin であれば誰でも判定可 | — | — |
| Origin 不一致 (CSRF, B-2) | **403** | `cross_site` |

副作用なし。

## バリデーション規約

- Zod（暫定）
- 順序:
  1. ボディスキーマ（reason 必須）→ 400
  2. authorize（role）→ 404
  3. proposal 取得 → `status='in_review'` 検証 → 422
  4. `assignee_id == viewer.user_id` 検証 → 404
  5. CAS UPDATE → 409

| 400 | `VALIDATION_ERROR` | reason 空 |

| 409 | `CONFLICT` | 楽観ロック |
| 422 | `BUSINESS_RULE_VIOLATION` | `status != 'in_review'` |
| 500 | `INTERNAL_ERROR` | 想定外 |
