# DB-004 — audit_logs（監査ログ・append-only）

## 概要

結果を変える 5 種・8 操作（submit / レビュー判定 4 種 / publish / withdraw / resubmit、`BR-PROPOSAL-01`、visibility 変更は RC-005 needs-clarification のため MVP 対象外）の成功時に 1 行 append される監査ログエントリ。`actor / actor_role / action / target / before / after / reason / timestamp` を必須フィールドとし（`BR-AUDIT-01`）、**append-only**（NFR-004 / `BR-AUDIT-02`）。

## カラム

| カラム名 | 型 | null | デフォルト | PK/FK/UK | 説明 |
| --- | --- | --- | --- | --- | --- |
| `id` | text | no | — | PK | エントリ ID。`crypto.randomUUID()` で生成（UUID v7 相当、Workers 互換）。最大長 36 文字。 |
| `actor_id` | text | no | — | FK → `users(id)` | 操作実行ユーザの `users.id`。`BR-AUDIT-01` の `actor` フィールド相当。 |
| `actor_role` | text | no | — | — | 実行時のロールスナップショット（記録時の `users.roles` のコピー）。複数ロール OR 合成時はカンマ区切り（例: `reviewer,admin`）。**ユーザの roles が後で変更されてもログ側は不変**（履歴の正確性を優先）。 |
| `action` | text | no | — | — | 操作種別。**MVP では 8 値**: `submit` / `start_review` / `approve` / `return` / `reject` / `publish` / `withdraw` / `resubmit` のいずれか（CHECK 制約）。RC-005 確定後に `visibility_shrink` / `visibility_expand` を追加して 10 値へ拡張。 |
| `target_proposal_id` | text | no | — | FK → `proposals(id)` | 操作対象の proposal。`BR-AUDIT-01` の `target` フィールド相当。 |
| `before_status` | text | yes | NULL | — | status 遷移前の値（`draft` / `submitted` / ... の 8 値、または NULL）。`action` が status 遷移系（MVP 全 8 操作）の場合は NOT NULL（アプリ層で正規化）。CHECK 制約は status の取りうる値（NULL 許容）。 |
| `after_status` | text | yes | NULL | — | status 遷移後の値。`action` が status 遷移系の場合は NOT NULL。 |
| `before_visibility` | text | yes | NULL | — | visibility 遷移前の値（`private` / `internal` / `public` または NULL）。**MVP では常に NULL**（visibility 変更は RC-005 needs-clarification）。RC-005 確定後に `visibility_shrink` / `visibility_expand` 操作で使用。 |
| `after_visibility` | text | yes | NULL | — | visibility 遷移後の値。MVP では常に NULL。 |
| `reason` | text | yes | NULL | — | 判断理由テキスト。**reason 必須操作** (`start_review` / `approve` / `return` / `reject` / `withdraw`) では NOT NULL（`BR-REVIEW-01` / `BR-PUBLISH-03`、CHECK 制約 + アプリ層検証）。**任意操作** (`submit` / `publish` / `resubmit`) では NULL 可（Q-019 暫定）。**最大長 4,000 文字**（暫定、m-13 整理: NFR-005 PII リスクと UX のバランス。長文の reason は通常不要であり、必要な場合は別途連携文書を `target_proposal_id` 経由で参照する運用。Phase 5 で UX レビュー時に再評価）。**PII を含めない運用**（NFR-005、AMB-012）。 |
| `policy_agreement_id` | text | yes | NULL | FK → `policy_agreements(id)` | 関連する PolicyAgreement レコード。`action='submit'` 時のみ NOT NULL（提出時の同意レコードへの参照）。`action='resubmit'` でも参照可（既存の同意を継続適用、Q-018 暫定、参照は記録）。それ以外の action では NULL。 |
| `created_at` | integer | no | — | — | 記録時刻（Unix epoch millis）。`BR-AUDIT-01` の `timestamp` フィールド相当。**append のみで設定し、UPDATE 不可**（NFR-004）。 |

> **型の方針（NFR-002 と整合）**: SQLite 互換の `text` / `integer` のみ。`action` / `before_status` / `after_status` / `before_visibility` / `after_visibility` の enum は `text` + CHECK 制約で表現。タイムスタンプは Unix epoch millis。
> **append-only の意味**: 本テーブルには `updated_at` カラムを持たない（更新が無いため）。`created_at` のみで十分。

## 不変条件

### 1. append-only（NFR-004 / `BR-AUDIT-02`）

- **アプリ層強制**:
  - AuditLog repository (`src/server/audit/repository.ts`) の export は **`append` / `findById` / `list` のみ**。`update*` / `delete*` の export は禁止（`BD-DATA` の Repository 表と整合）。
  - CI grep で `update*AuditLog` / `delete*AuditLog` パターンが 0 件であることを観測（NFR-004 AC）。
  - 命名規約として、AuditLog repository に対する関数は `update*` / `delete*` プレフィクスを **使わない**（`patch*` / `remove*` 等の同義語も同様に禁止、レビューで強制）。
- **DB 層強制（Phase 3 で確定）**:
  - Q-005 確定後（D1 採用時）に「採用ストアの機能で update / delete を制限する設計」を `02-architecture.md` に記録（NFR-004 AC）。具体案: D1 では `BEFORE UPDATE` / `BEFORE DELETE` トリガで `RAISE(ABORT, '...')`、または別アカウント（書き込み専用 DB ロール）で `audit_logs` テーブルの `UPDATE` / `DELETE` 権限を剥奪。
  - MVP（in-memory）では「Repository が export 関数を持たない」ことが唯一の強制手段（アプリ層強制のみ）。

### 2. reason 必須・任意の整合（`BR-REVIEW-01` / `BR-PUBLISH-03` / Q-019 暫定）

- reason 必須操作（5 種）で `reason IS NULL` または `reason = ''` の append 試行は **アプリ層で `400 VALIDATION_ERROR`** にし、AuditLog エントリは作らない（`BR-AUDIT-03`、reason 空の API 呼び出しは status 遷移自体が失敗）。
- DB 層 CHECK で表現可能だが（`CHECK ((action IN ('start_review','approve','return','reject','withdraw') AND reason IS NOT NULL AND reason <> '') OR (action IN ('submit','publish','resubmit') AND TRUE))`）、可読性のためアプリ層を一次強制とし、DB 層 CHECK は **追加防御線として導入予定**（Phase 5 の D1 移行時）。

| action | reason | 根拠 |
| --- | --- | --- |
| `submit` | 任意 (Q-019 暫定) | REQ-002 / `BR-PROPOSAL-03` |
| `start_review` | 必須 | REQ-003 / `BR-REVIEW-01` |
| `approve` | 必須 | REQ-003 / `BR-REVIEW-01` |
| `return` | 必須 | REQ-003 / `BR-REVIEW-01` |
| `reject` | 必須 | REQ-003 / `BR-REVIEW-01` |
| `publish` | 任意 (Q-019 暫定) | REQ-004 |
| `withdraw` | 必須 | REQ-005 / `BR-PUBLISH-03` |
| `resubmit` | 任意 (Q-019 暫定) | REQ-006 |

### 3. status / visibility 列の整合

- `action` が status 遷移系（MVP の 8 値すべて）の場合、`before_status` / `after_status` は NOT NULL（アプリ層で正規化）。MVP の status 遷移は次のとおり:
  - `submit`: `before_status='draft'`, `after_status='submitted'`
  - `start_review`: `before_status='submitted'`, `after_status='in_review'`
  - `approve`: `before_status='in_review'`, `after_status='approved'`
  - `return`: `before_status='in_review'`, `after_status='returned'`
  - `reject`: `before_status='in_review'`, `after_status='rejected'`
  - `publish`: `before_status='approved'`, `after_status='published'`
  - `withdraw`: `before_status='published'`, `after_status='withdrawn'`
  - `resubmit`: `before_status='returned'`, `after_status='submitted'`
- `before_visibility` / `after_visibility` は **MVP では常に NULL**（visibility 変更操作が無いため）。RC-005 確定後に `visibility_shrink` / `visibility_expand` 操作で使用開始。
- 認可エラー（`401` / `403` / `404`）で失敗した呼び出しでは AuditLog エントリは生成しない（`BR-AUDIT-03`）。

### 4. actor_role と action の組合せ整合（`BR-AUTHZ-01`）

- アプリ層検証（authorize 層通過後の値を append 時にスナップショット）:
  - `action='publish'` / `action='withdraw'` の場合、`actor_role` に `admin` を含む（`BR-PUBLISH-01` / `BR-PUBLISH-03`、admin 専権）。
  - `action='start_review'` / `approve` / `return` / `reject` の場合、`actor_role` に `reviewer` または `admin` を含む（REQ-003）。
  - `action='submit'` / `resubmit` の場合、`actor_role` に `user` を含む（投稿者本人、REQ-002 / REQ-006）。
- DB 層では強制せず、アプリ層 + テストで担保。違反した append が発生した場合はバグであり、CI / E2E で検出する。

### 5. PII 除外（NFR-005 / AMB-012）

- `reason` テキストには **投稿本文 / メールアドレス / 個人特定情報を含めない** 運用ガイドライン（NFR-005 PII リストの「投稿コンテンツ」相当）。システム強制は AMB-012 で別途検討（Phase 2 以降）。
- logger 出力時は `reason` フィールドを **出力しない**（NFR-005、許可フィールドホワイトリスト外）。`audit_log_id` で AuditLog 詳細 (API-017) へ追跡する。

### 6. policy_agreement_id の整合

- `action='submit'` の場合のみ NOT NULL（初回提出時に新規生成された PolicyAgreement の `id`）。
- `action='resubmit'` の場合、既存の `current_policy_agreement_id`（DB-003 の `proposals.current_policy_agreement_id`）の値を **コピーして記録**（参照を残すことで、後から「どの policy version の同意のもとで再提出されたか」が追跡可能）。
- それ以外の action では NULL。アプリ層で正規化。

## マイグレーション方針

### 追加（カラム追加）
- 後方互換: **`null` 許容で追加 → バックフィル → `not null` 化** の 3 ステップ。
- AuditLog は append-only のため、**過去レコードの UPDATE は禁止**。バックフィルは「新規カラムを `null` のまま運用継続」を選択し、過去エントリは null のままにする（既存データの整合性を犠牲にしない）。

### action enum の拡張（RC-005 確定後）
- `action` の CHECK 制約に `visibility_shrink` / `visibility_expand` を追加。
- `before_visibility` / `after_visibility` を `visibility_*` 操作で NOT NULL 化（アプリ層）。
- 関連 AC: REQ-011 の AC を更新。

### MVP DDL（D1 移行時、SQLite 互換）

```sql
CREATE TABLE audit_logs (
  id                   TEXT NOT NULL PRIMARY KEY,
  actor_id             TEXT NOT NULL REFERENCES users(id),
  actor_role           TEXT NOT NULL,
  action               TEXT NOT NULL
                         CHECK (action IN (
                           'submit','start_review','approve','return','reject',
                           'publish','withdraw','resubmit'
                         )),
  target_proposal_id   TEXT NOT NULL REFERENCES proposals(id),
  before_status        TEXT
                         CHECK (before_status IS NULL OR before_status IN (
                           'draft','submitted','in_review','approved',
                           'returned','rejected','published','withdrawn'
                         )),
  after_status         TEXT
                         CHECK (after_status IS NULL OR after_status IN (
                           'draft','submitted','in_review','approved',
                           'returned','rejected','published','withdrawn'
                         )),
  before_visibility    TEXT
                         CHECK (before_visibility IS NULL OR before_visibility IN (
                           'private','internal','public'
                         )),
  after_visibility     TEXT
                         CHECK (after_visibility IS NULL OR after_visibility IN (
                           'private','internal','public'
                         )),
  reason               TEXT,
  policy_agreement_id  TEXT REFERENCES policy_agreements(id),
  created_at           INTEGER NOT NULL
);

CREATE INDEX ix_audit_logs_target_proposal
  ON audit_logs(target_proposal_id, created_at);
CREATE INDEX ix_audit_logs_actor
  ON audit_logs(actor_id, created_at DESC);
CREATE INDEX ix_audit_logs_action
  ON audit_logs(action, created_at DESC);
CREATE INDEX ix_audit_logs_created_at
  ON audit_logs(created_at DESC);
```

> **DB 層強制の追補（Phase 3 で確定予定）**:
> - D1 では `CREATE TRIGGER audit_logs_no_update BEFORE UPDATE ON audit_logs BEGIN SELECT RAISE(ABORT, 'audit_logs is append-only'); END;` 等のトリガで update / delete を防御。
> - または別アカウント分離: アプリの DB ユーザには `audit_logs` テーブルへの `INSERT` / `SELECT` のみ付与し、`UPDATE` / `DELETE` 権限を付与しない。
> - 採用方式は Q-005 確定後の `02-architecture.md` で記録。

### 保持期間（Q-006 / NFR-007）
- Q-006 確定までは **保持期間を定めない**（MVP は `wrangler tail` リアルタイム閲覧 + DB 永続化のみ）。
- Q-006 確定後に「最終ログ出力から N 日以内は集約先で検索可能」等を NFR-007 AC に追記し、本ファイルの「マイグレーション方針」に物理削除運用を記述する（**append-only の例外として、保持期間超過分の bulk delete は admin 操作 + Reflection Plan 経由でのみ許可**、運用は Phase 3 末で確定）。
