# DB-006 — users（モック認証ユーザ）

## 概要

モック認証（REQ-015）におけるユーザ識別子とロールを保持するエンティティ。実体は **環境変数の許可リスト**（cookie 値 → ユーザ識別子・ロール）であり、本テーブルは許可リストから読み取った内容を「現在ログイン中のセッション主体」として参照するためのキャッシュ・代理表現として位置付ける。書き込みは環境変数管理であり、API 経由の登録 UI は MVP 非対象。

> 注記:
> - `guest` ロールは「cookie が無い／許可リスト外」の状態を表すため **本テーブルにレコードを持たない**（cookie のないリクエストは `guest` 扱い、REQ-015）。
> - MVP は in-memory 実装（許可リストパース結果を起動時にメモリ展開）で start。Q-005 でデータストアが D1 に確定した場合は、本ファイルの DDL を SQLite 互換のままマイグレーション化する。
> - 本ドメインでは既存サンプル DB-001（users）は AMB-001 で人間判断待ちのため温存し、本エンティティ DB-006 を採用する。

## カラム

| カラム名 | 型 | null | デフォルト | PK/FK/UK | 説明 |
| --- | --- | --- | --- | --- | --- |
| `id` | text | no | — | PK | ユーザ識別子（不透明 ID）。`crypto.randomUUID()` で生成（Web Crypto API、Workers 互換）または許可リストで明示指定された任意文字列。`AMB-008` 暫定: 不透明 ID は PII 非該当。最大長 128 文字（DDL 制約はかけず、許可リストパース時にバリデーション）。 |
| `display_name` | text | yes | NULL | — | 画面表示名。**PII 該当の可能性あり**（NFR-005 PII リスト「識別子」に準ずる扱い）。logger には出力しない。最大長 128 文字。 |
| `roles` | text | no | — | — | カンマ区切りロールリスト。`^(user|reviewer|admin|auditor)(,(user|reviewer|admin|auditor))*$` の正規表現に合致すること。重複・順序非依存（OR 合成、REQ-010 / `BR-AUTHZ-01`）。 |
| `created_at` | integer | no | — | — | 作成時刻（Unix epoch millis）。許可リストから取り込んだ時点のタイムスタンプを記録。 |
| `updated_at` | integer | no | — | — | 最終更新時刻（Unix epoch millis）。許可リスト再読み込み時に更新。 |

> **型の方針（NFR-002 と整合）**: SQLite 互換の `text` / `integer` のみを使用。タイムスタンプは Unix epoch millis（タイムゾーン依存を排除）。UUID 専用型 / `timestamptz` / `serial` は使用しない。

## インデックス

| 名前 | カラム | 種別 | 用途 |
| --- | --- | --- | --- |
| `pk_users` | `(id)` | primary | 主キー検索（cookie → ユーザ参照） |

> 注記: 本エンティティは「許可リスト由来のキャッシュ」であり、ユーザ数が小さい想定（MVP では数〜十数）。`roles` の部分一致検索やフィルタ用途のインデックスは MVP 段階では追加しない。

## 不変条件

1. **roles 形式**: `roles` は CSV 形式で、`^(user|reviewer|admin|auditor)(,(user|reviewer|admin|auditor))*$` の正規表現に合致する。検証は **アプリ層**（許可リストパース時 + repository 入口）で行う。DB 側 CHECK 制約は SQLite 互換のため CHECK で表現可能だが、許可リスト変更時のエラーを早期に検知するためアプリ層を一次強制とする。
   - **正規化（m-07 整理）**: 正規表現は重複（`user,user`）や順序違い（`auditor,user`）を許容してしまうため、**CHECK 制約後にアプリ層で正規化する**: (1) 小文字化、(2) アルファベット昇順ソート（`admin < auditor < reviewer < user`）、(3) `Set` で重複除去 → 再度 CSV join。例: 入力 `User,Admin,user` → 正規化後 `admin,user`。正規化済みの値を DB に保存し、AuditLog の `actor_role` も同じ正規化結果を使用する（DB-004 不変条件 4 と整合）。
2. **guest はレコードを持たない**: `guest` ロールはセッション主体を持たない（= cookie が無い／許可リスト外）。本テーブルに `roles=guest` のレコードを作らない（REQ-015 / `BR-AUTHZ-01`）。
3. **PII の扱い（M-2 整理）**: `display_name` は **表示専用フィールド** として扱う。レスポンス body / 画面表示には使ってよいが、**logger 出力 / エラーメッセージには出さない**（NFR-005 PII 配慮の拡張、AMB-008 暫定方針）。最終的な PII 該否判断（cookie 値・display_name の運用上の取扱・hash 化要否を含む）は Phase 6 入口（実装着手時）で再評価する。`id` は不透明 ID なので `user_id_hash`（NFR-007）として hash 化して logger に出すことは可。
4. **書き込みは環境変数管理**: アプリの API（server function / loader）からの `INSERT` / `UPDATE` / `DELETE` は行わない。書き込みは「起動時に許可リストをパースして同期するバッチ処理（MVP では in-memory 構築）」のみ。Repository インターフェイスは `findById` のみを export する（`create` / `update` / `delete` は export しない、`BD-DATA` の Repository 表と整合）。
5. **id の不変性**: 一度払い出した `id` は許可リスト変更時も再利用しない（過去の AuditLog / proposals / policy_agreements の FK が宙に浮かないようにするため）。許可リストから削除されたユーザに対しては DB レコードを残し（過去操作の追跡可能性のため）、`roles` を空文字 `""` に更新する運用は **MVP では行わない**（許可リストの状態を即時反映する代わりに、過去レコードは現在の `roles` を保持し続ける）。最終運用は Phase 3 末で確定。

## 関連 API

| API-019 (`login`) | read | cookie 値を許可リストに照合し、合致したユーザを `findById` で取得してセッションを確立。公開バイパス対象（UC-013 認可境界の対象外）。 |
| API-020 (`logout`) | — | セッション cookie を破棄。本テーブルには触れない。 |
| API-002 〜 API-009 (mutation 系) | read | 認可ヘルパー (`src/server/auth/authorize.ts`) が `findById` 経由で actor の roles を確認（`BR-AUTHZ-03`）。 |

> **読み取り経路の正規化**: アプリのすべてのロール判定は `findById` の結果（= `roles` フィールド）を介して行い、cookie の生値からロール判定を直接行うことは禁止する（`BR-AUTHZ-03` と整合）。

## マイグレーション方針

### 追加（カラム追加）
- 後方互換性が必要な場合は **`null` 許容で追加 → バックフィル → `not null` 化** の 3 ステップ。
- 例: `email_hash`（将来メールアドレス採用時）を追加する場合は、既存ユーザを許可リストから再生成しつつ段階適用。

### 削除（カラム / レコード削除）
- カラム削除は参照解除を先に行い、トランザクションログ保持期間内に完了させる。
- レコード削除（許可リストからの削除）は **MVP では行わない**（過去の AuditLog / proposals の FK が宙に浮くため、不変条件 5 を参照）。Phase 3 末で「論理削除フラグの追加」を再評価する。

### MVP からの移行
- MVP は in-memory（許可リストパース結果のメモリ展開）で start。Q-005 確定後（D1 採用時）は本ファイルの DDL を以下の SQLite 互換 DDL としてマイグレーション化する:

```sql
CREATE TABLE users (
  id           TEXT NOT NULL PRIMARY KEY,
  display_name TEXT,
  roles        TEXT NOT NULL,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);
```

> 注記: `roles` の正規表現 CHECK 制約は SQLite では `CHECK (roles GLOB '...')` で限定的に表現可能だが、可読性のためアプリ層を一次強制とする。
